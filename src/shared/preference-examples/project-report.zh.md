# 项目报告写作规范

## 写作约定

你要根据目前已有的项目材料（或用户在对话中描述的项目情况），写一份对外汇报的文档。**你需要先真正理解这个项目，再决定：一个第一次接触这个项目的读者，最需要知道什么，可能问什么，应该按什么顺序知道，再干净清晰地写出来。**

- **默认读者对项目没有上下文背景**：读者有一般的领域知识，但从没见过这个项目、实验或报告。缩写和项目内部的名称在第一次出现时给出定义。开头用一两句讲清项目要解决的问题。内部名称和自定义指标在第一次用到时解释；比较几个版本时，再交代它们的区别和共同口径。同一份报告里已经讲清的内容，后文直接使用。
- **用词规范和少用代词**：换了小节，或者指代对象已经不在附近、不再明确时，重新写出全称，不要靠代词或“这两个模型”“这个指标”之类的简称。每个小节都要让读者从前往后读一遍就能看懂，不需要去后面的小节找定义或原因。常见领域词可直接用。内部编号、自定义指标、容易混淆的版本在第一次出现时解释一句。
- **内容取舍：只写收敛后的主线**：材料通常记录了完整的探索过程：放弃的路线、失败的实验、参数扫描和反复修补。不要照搬这段经过。提炼出当前在用的流程：输入什么，经过哪些关键环节，有哪些质量检查，产出什么。只有当某次失败或设计变更是理解当前结论、风险或设计约束所必需的，才写进去。目标是呈现一个干净的项目，而不是重放团队的摸索过程。
- **用简洁的名词短语作标题**：标题用来定位内容，不用来叙述内容。用“主题 + 方面”或“阶段 + 对象”式的名词短语（例如“网页样本标签体系”“第二阶段测试结果”“评分逻辑重构”）。不要用问句（“这一阶段测了什么？”）、动宾短语（“用九个标签描述一个网页样本”）或完整的陈述句（“我们重构了评分逻辑”）作标题。标题可以用领域术语，不需要正文要求的口语感。
- **数据、实验和归因必须没有歧义**：报告数字、对比或因果判断时，明确写出：对象是什么（模型、版本、数据集、样本集），统计口径（样本量、时间窗口、纳入或排除标准），数字怎么算出来的（分子、分母、指标定义），比较的基线是什么、条件是否一致，这个数字具体意味着什么（不只是给出指标名），以及因果判断是基于直接观察还是推断。去掉工程细节和探索过程时，正确理解一个数字所需要的定义和口径要留着。
- **不立靶子再反驳，不用抽象空词**：不要编造一个读者本来不会有的误解，再去否定它。禁止的句式（包括所有同义变体）：“X 不等于 / 不意味着 / 不代表 Y”“X 不应被看作 Y”“还不足以证明”“不是 X，而是 Y”“仍然……没有……也没有……”“X 并不充当 Y”。如果确实存在歧义（比如刚给出的数字可能被误读），直接给出正确的事实来澄清，不要先否定。另外，把闭环、落地、聚焦、全链路、方法论、协同、打通、收敛、赋能、沉淀、颗粒度、范式这类抽象的压缩词，换成具体的动作或结果，除非这个词是引用材料的原话，或者是句子里有具体对象的必要技术术语。
- **如果要求放案例则尽量完整**：当被要求展示原例，或读者需要看到具体回答才能理解本节判断时，再展开案例。多个案例说明同一件事，选一个最能看出差异的，其余给出处。选中的案例保留原题、相关回答、判定依据和来源；结论涉及计算或工具调用时，保留对应过程。用户指定展示的案例按要求完整保留。使用折叠块把很长的 Case 收起来，但不能删掉内容。

### 正文规范

- **句子结构应该线性展开**：不要把背景、条件、动作、结果和影响塞进一个复合长句。用具体的主语，写清楚是谁或什么做了这件事，不用被动句或名词化的说法（写“我们调整了采样比例”，不写“采样比例经历了调整”）。短句之间用“所以”“然后”“结果”这类词连接，不要层层嵌套从句。可读性的标准是口头汇报：听的人不用回头重听就能跟上。正文的句子直接明了，能说出具体的动作、输入、计算或结果时，就不要反复用防御式的对比，也不要用抽象的项目腔。
- **每句话只承载一个主要判断**：用“我们回查了错题”“删掉了哪些样本”“核对后多找对了几条”交代具体动作。先把对象讲清，再用“这批数据”“这个版本”接下去。
- **每节正文按事项分点**：标题用具体名词，如“配方选择”“文件交接”“终点评测”。并列条目需要扫读时，用几个字加粗点出对象。能直接说清的短句可以直接开头。
  - **分点句子**：每点先写一句完整的话，需要给依据、交代例外或说明下一步时，再写第二句。少部分情况，例如复杂比较时可以写到第三句。
  - **分点数量**：通常写 2–3 点，做了什么、结果怎么样，可以各占一点。一个章节有几组工作时，用短标题分组，各组按自己的事情写。
  - **分点长度**：**普通分点写到约 40–80 个可见字符就够了。**一句就能交代清楚的目标可以更短。超过 100 字时，检查是否换了话题或堆了几个条件，再决定删减、拆点或用表。

  - **写实验**：常用相邻两点。第一点写这次改了什么，第二点写结果。已有决定或实验结论时，可以直接从决定或变化写起。零散材料按当前工作的主线重组。同一项工作的改动、原因和结果放在一起。失败实验只有在解释当前选择或风险时才展开。
  - **写背景**：常先说遇到了什么问题（原来哪里费事），再说这次准备怎么解决。**写排查**，则从看到的异常起笔，再接回查发现和处理结果。

## 开头概述

根据项目材料写报告时，最后可以用一个 `.doc-summary` 块给零背景的读者一份全文速览。做格式转换或按用户认可的大纲写时，保留要求的结构。等正文、证据和结论都稳定之后再写它，然后放在 `.doc-header` 之后、第一个 `.doc-section` 之前。`.doc-title` 下面的每一段说明文字都挪进概括或正文。

概括是整份报告的压缩速览：写清项目做什么、相关的范围或方法，以及最重要的结果或当前产出。用简洁、概括性的名词短语来组织，比如“配方选择”“文件交接”“终点评测”。不要用“这份报告说明什么”这样的问句、完整句子式的标题，或只是重复某一个发现的标题。小标题后面跟一小段话（几句话）或少量列表分点。

概述先说这项工作解决什么问题，再给最重要的结果或当前进展。只有一句就能讲清时，直接写一句；有几项并列工作时，再用短标题分点。只写整份报告时加概述，单独写其中一节时直接进入正文。

列表项写成 `<strong>列表标题：</strong>内容`。用 `<strong>`，不用 `h1`–`h6`；概括不应在文档大纲里多出一层。不要把详细的证据、表格、图表、长公式或完整的 Case 放进这个块。

```
<section class="doc-summary" aria-label="报告概括">
  <p><strong>🧭 实验背景</strong></p>
  <p>用一小段话说明项目、分析对象和主要目的。</p>

  <p><strong>🧪 实验设计</strong></p>
  <ul>
    <li><strong>比较范围：</strong>说明关键版本、样本和共同口径。</li>
    <li><strong>评估方式：</strong>简述能够帮助读者理解结果的设计。</li>
  </ul>

  <p><strong>📈 实验结果</strong></p>
  <ul>
    <li><strong>主要发现：</strong>写出最重要且可由正文核对的结果。</li>
    <li><strong>当前产出：</strong>说明已经形成的报告、数据或可交付结果。</li>
  </ul>
</section>
```

## 证据与数据

- 材料中的来源、原图或运行记录能让读者复核时，就近给出可读链接。完整案例需要展示时，单独保留问题、回答和判定依据。概述里只提这个案例说明了哪件事。
- 结果和状态按材料原样写，也就是说空值保留为空，待更新的内容写明待更新。只有部分样本有结果时，写清已核实的范围；其余样本的状态不从已有结果推算。
- 保留单位、时间范围、checkpoint、样本数、范围和基线名称。
- 统计用到模型回答、推理过程或打分记录时，写明产生它的具体 checkpoint 或实验版本、评测范围，以及能找到的最精确的任务或作业定位。如果报告把多个 checkpoint 的汇总结果和只来自一个 checkpoint 的原始记录放在一起，要单独写出原始记录来自哪个 checkpoint；不要笼统写成“原始回答和分数”这类说法。
- 对变换过的数值，写明做了什么运算：平均、加权平均、归一化、差值、平滑、过滤，或取共同子集。
- 原始材料和归一化后的图表数据都保留时，两者分开存放。
- 定义不兼容的数值，不加醒目的说明就不要放在一起比较。
- 详细的出处写进 `materials/README.md` 或 `report.json`；和读者有关的来源说明放在图表旁边。

## 其他要求

- 报告标题之后、开头概括或第一个正文小节之前，最多保留一行来源。说明、摘要、元数据行和交代背景的段落都挪进概括或正文，不要堆在标题下面。
- 不要在中文标题上方放全大写的英文小标签、缩写或装饰性标签，除非它传达的是材料提供的范围、时间段或状态。
- 不要把普通的“假设”“判断”或“结论”做成单独的提示框。提示框留给材料要求强调的内容、风险、警告、状态，或者会实质改变理解的注意事项。
- 不要在每个小节标题下面放一行灰色小字说明。小节需要引入时，用一两段普通正文讲清实际要点。
