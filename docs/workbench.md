# Workbench

`npm run dev:local` serves the workbench at `http://127.0.0.1:8080/`: the documents in a sidebar (their outline, favorites, search, a trash), one open in an iframe with its own editor, and the commands on whole documents (new, duplicate, rename, move, trash and restore, export). The app is `src/workbench/app/` (React), its server side `src/workbench/service.mjs`. After it, this file specifies the contract it keeps with the rest of Gallery, which any other workbench keeps too: the **session protocol** between an open document page and the workbench (`postMessage`), and the **workspace commands** of `dev:local` (`/__gallery/workspace/*`, HTTP).

**Sandbox.** `gallery sandbox` starts the production service with a private workspace, data directory and cache on an OS-assigned loopback port. Its name appears in `GET /__gallery/workspace/info` as `server.sandbox` and in `GET /__gallery/workspace/outline` as `sandbox`. The workbench shows a short 沙盒 banner above the content and hides the menu item for attaching another workspace. The service also refuses that operation if a client requests it directly. The sandbox's own folders (its root under the real temporary folder, its box, home, data and cache), which it removes, may hold no link at all and must each be their own real path (`checkedDirectory`). An `--extension` folder is only read: the links on the way to it are resolved first (`extensionSource`: the real path of its parent and its own name; macOS's `/tmp` is `/private/tmp`, a Windows junction, an 8.3 name), so `gallery extension check` works in a workspace reached through one; the folder itself being a link is refused (扩展文件夹本身不能是符号链接), as install refuses such a source and the watcher would follow it out of the folder named.

- **A document's link** in the address is its title's words and its page id (`#项目周报-Q3-k3xv9q2a`, `src/shared/page-links.mjs`): the words of the title, the rest dashes, then the id; a title that leaves no words is the id alone. A page id has the look of a block id, eight letters and digits with a letter first, and is worked out from the folder name (`pageId`, pure, the same on the server, in the workbench and on a page: a hash of the name, but for a name of the shape `doc-` and eight characters, a lowercase letter and then lowercase letters or digits (`DOC_SLUG`), whose id is those eight, so that the folder `doc-tacti90g` has the address `#反馈文档-tacti90g`; every other name keeps the id it always had, a near miss such as `doc-Abcdefgh`, `doc-abc` or `doc-abcdefgh-2` among them; and a folder of that very shape made before, an Agent's `doc-overview` whose address was `#Overview-f3md3kg4`, keeps that address besides, its hash being its `earlierId`: `pageOfLink` reads an id by the folders' own eight first, then by an earlier id, so that every address written down before still opens it, and `newDocSlug` never picks an id such a folder had), which is the document's identity: a title never changes it. So nothing is kept: no file, no list to keep in step, and a page alone in a tab or with no list read can always say its own address. The words are a label. A link is read by what stands after its last dash (`pageOfLink`), so an address written down before a rename opens its document for ever, the address bar then saying the title of now, and two documents of one title need nothing to tell them apart. The link follows a title as it is typed, as the sidebar does, the h1 the page shows counting, saved or not, its `doc.json` holding the same or not. ## Contract

The settings menu groups 组件列表, 拓展列表 and 开机自启动 under 功能, separate from 偏好 and 语言. Settings is as wide as the rows it covers (`.ws-menu`: the sidebar's width less its two 8px margins, 240px at least and 320px at most; 254px at the default width); its trash submenu keeps the `settings-menu` width of 240px; other wide popovers keep their own sizing. Its leading icons are drawn as every menu row's (Menus and popovers, above: own 20-unit drawings at 20px, Lucide's at 18px, about 1.25 on screen); their color comes from the shared menu icon token. The language globe reuses the web icon drawing. Import, trash, editing frame, bell and change indicators keep their meanings in this common specification, including wherever those shared icons are reused.

Two rules hold throughout:

- A document's `doc.html` (`<workspace>/<slug>/`; `report.html` in one made before Gallery 0.1, read and written under that name: [internals.md](internals.md) "Where things live") stays the only source of a document. The workbench never stores or sends document content; what the workspace service keeps of its own is under the workspace's `.gallery/`: the outline (`outline.json`: which document sits under which, in what order), the trash (`trash/`) and the 写作偏好 page (`pages/<slug>/`). A custom page's `page.html` and `page.json` (`<home>/pages/<slug>/`) are its only source as well.
- The workbench and the document pages share one origin. Messages are posted to that origin only, and the commands check Host, Origin and the token as a commit does. The built-in workbench is served by `dev:local` itself. A workbench served by a dev server of its own proxies `/generated`, `/__gallery`, `/kit` and `/vendor` to `dev:local`, with the Host rewritten to `dev:local`'s (`changeOrigin`). Only for requests from its own page (Origin equal to the workbench's address) does it also rewrite the Origin to `dev:local`'s; anything else passes unchanged and is refused as before.

### Session protocol

The document page runs the session when it is in an iframe (`src/editor/page/session.mjs`; the protocol's constants are `src/shared/session.mjs`); on its own it does nothing. Every message is

```js
{ protocol: "gallery/session", v: 2, type, slug, ...fields }
```

posted with `targetOrigin` set to `location.origin`. Both sides require the exact same origin, the expected source window, the protocol/version and the current session identity. Project documents use the same channel: their HTTP path has an owner prefix, and workbench identities retain `~<ws-id>/` to distinguish equal slugs. Browser recovery buffers, view state and edit broadcasts likewise include the owner.

The browser tab shows the open document's icon too (the same image with `&tab=1`: a set's icon in its own color; the top bar sets the workbench's `link rel="icon"`, blank without one), as the title is the tab's text. `state` is (`STATE_FLAGS` in `src/shared/session.mjs`):

| field | meaning |
| --- | --- |
| `editing` | the editor runs (a document's page edits from the start) |
| `pending` | changes wait to be saved (for a pause in typing), or are on their way |
| `saving` | a commit is on its way |
| `offline` | commits do not get through; the changes wait in the browser and go once they can |
| `conflicts` | how many things wait for the reader in the page: conflicts and what the file cannot hold (a number) |
| `unfit` | how many of those the file cannot hold, no conflict with a newer version (a number) |
| `changed` | someone else wrote the file (an Agent, another tab); the page shows it once nothing waits |

When its file changes, the page asks to be shown again (`reload`) once nothing waits there; the new page sends `ready`. On its own (no workbench), it reloads itself.

### Workspace commands

Gallery's server (npm run dev's, or one a gallery command started) answers `/__gallery/workspace/<name>` (`src/workbench/service.mjs`). A page asks it too: `GET outline` once for each opening of a link card, a page block's box or "@", and to hold the list ready for a copy (`editor/page/links/pages.mjs`; no route of its own, nothing pushed), `POST create` for a new subpage, with the token of its edit map. A GET needs the server's exact Host. A POST is checked as a commit is (Host, `Origin`, the `X-Gallery-Token` header, a JSON body) and runs in the same queue as commits, one at a time. Answers are JSON, `{ ok: true, ... }` or `{ ok: false, reason, message? }` with an HTTP status to match (400 bad request, 403 refused, 404 missing, 409 conflict, 422 checks failed). `message` is the server's Chinese; one with parts filled in (a size, a name, the check's lines) also carries its template and parts, `text` and `values` (`said()`, `src/shared/i18n/`), which the UI says in its language (`told()`: `t(text, ...values)`, else `t(message)`; the parts as they are), as every answer of the edit service (`/__gallery/edit/*`) and `/__gallery/transfer/*` does. A document is named by its slug; the server makes new slugs, and paths never leave the workspace.

**Favorites** (收藏) are the one thing of the sidebar a browser keeps itself (localStorage, `workspace/store.ts`) that a command also reaches: `gallery favorite` writes the shared list, `favorites.json` in the user's data folder (beside the registry of workspaces; never a workspace's files: a star is the reader's, so a workspace synced or shared carries none, and the outline file holds no `favorites`), `GET outline` gives that list, and the workbench merges it with its own whenever it reads the list (`mergeFavorites`, `src/shared/favorite-merge.mjs`): an entry the file gained joins the browser's, one the file dropped since this browser last read it (`gallery favorite --off`) leaves it, one only the browser has is pushed to it (`POST favorite`), and a star the reader sets or takes away is told to it as well; the browser's order stays. The outline retains version 2: `{ version: 2, children, groups }`. The default workspace owns the shared file; its local entries use plain slugs and other entries use `~ws-<id>/<slug>`. A custom column can carry `owner`; workspace columns carry `workspace`; extension columns remain `{ id: "ext-<id>", extension: "<id>" }`, with no tree entries. Per-window projection is reversible and does not copy document files or store a second tree. Project-local files retain sidebar `head` and optional `extensionPositions` for private extension columns. Shared writes use the existing default outline lock and `POST outline` base/stale guard. The lock has a heartbeat; a waiting writer times out instead of stealing an active lock. Each server watches the shared outline even when the default workspace server is not running, then uses the existing workspace event and refresh path. The standalone reader continues accepting older versions and flags.

Every change of the outline is read, made and written under its lock (`withOutlineLock`, `.gallery/outline.lock`: a file made with `wx`, which one process alone can make, taken over when older than 10s), the server's in its queue and a command's with no server running alike, so that two writers (the workbench and an Agent's `gallery move`, or several of an Agent's commands run at once) never lose each other's change: a command and the server make their change on the outline read under the lock, and the workbench, which sends a whole tree made from the outline it read, has it refused when that is no longer what is read (`POST outline`'s `base`) and makes its change again on the outline read now; each write the server makes is told on the workbench's event stream. What the outline does not hold (favorites, which document is open, sidebar widths) is the workbench's own state and stays in its own storage. `.gallery/` starts with a dot, so document listing, previews, checks and packaging skip it (the preview's watcher too, but for the 写作偏好 page's folder, `.gallery/pages/<slug>/`, whose commits its other pages hear as any document's). `components/`, the custom blocks, holds no document, so the same walks pass it by, and a new document never takes its name: the workbench's next free name is `components-2`, and a document of that name back from the trash comes back as that. One made before the custom blocks came stays a document in that folder; `duplicate` and `trash` take what is its own and leave the custom blocks' scopes.

### The workspace's facts

Concurrent reads of all documents (for example the home page's recent, to-do and statistics cards) share one in-flight scan. Each caller gets its own list to sort. The scan is discarded on completion, failure, a document change or explicit invalidation; later queries still check files on disk instead of waiting for a cache timeout.

A to-do is read by `src/shared/todos.mjs` (`todosOf`), the one reading of the facts and of a check from another page (`src/editor/todos.mjs`), with `at` (its <li>'s offset) where the editor names it. A keyed table of a document (`table`: `{ slug, key, where?, limit? }`, 200 rows by default, 1000 at most) is read of its text as the kit reads one on a page (`src/shared/file-table.mjs` `keyedTable`, whose `tableCells` the checks read a chart's table by too): the first frame carrying the key (none a template holds, nor an instance's own region), `{ columns, rows: [{ values, links }], total }`, the rows whose cells hold the words `where` names (as written, blanks tidied), the first `limit` of them, `total` how many matched; its reading kept with the document's entry until the file changes. Which tables each document's instances asked for (`&doc=`) is kept in `.gallery/cache/workspace/<slug>.json` (`{ tables: ["<slug>#<key>"] }`, the last 20, losable), and `snapshot(slug)` gives what an export of it embeds (`SNAPSHOT_LIMITS`): `todos` (200, done or not), `recent` (50), `stats`, `activity` (371 days), its own `document` and those `tables` (1000 rows each, with each cell's words, which a query of the export filters by), asked by the export only of a document holding a block whose needs hold `workspace` (`render/net-snapshot.mjs`, beside the net's; the server's facts for the workbench's 导出 and the export dialog, a facts index of its own, the record read and never written, for `gallery export`). `table` is told as changed (`data table`) whenever a document's text did.

What a block reads of the workspace is kept by the server side of the workbench, beside its service: `src/workbench/index.mjs` (`createIndex`), one for the server (`src/server/routes.mjs` makes it and hands it to the service, which answers `GET query` from it and reads its search's lines and its menus' counts through it, so that a document is read once for all three). Per document (the outline's, at the root: never the 写作偏好 page, a scratch copy of `gallery block try` or a custom page): its title and icon (`doc.json`), `created` (when it was made: `doc.json`'s `created`, an ISO time that `createReportFromStarter` writes as Gallery makes a document, gallery new and import and the workbench's 新建, and that a copy, `copyEntryFiles`, writes anew for itself, a duplicate's and a copy to another workspace's; for a document with none (made by hand, or before Gallery wrote it), the earliest of its folder's birth time and its files' times, as a folder copied from elsewhere is as new as the copy while its files often keep their times: `createdOf`), `edited` (its file's time), its words (as the menus count them), the hash of its file's text and its to-dos (`todosOf`: each item of a `ul.doc-todo`, its own words, a nested list's and a held block's apart, or its first block's where it holds none of its own; `done`, `data-checked`; its `data-block-id` or null; `path`, the headings above it, the outermost first, the title none; `nth`, which of the to-dos of the same words under the same path it is), all of it read of the document as its pages are served it (`readOf`, the edit service's `readTaken` at once: an Agent's natural HTML the kit's, nothing written, and never a file held half written, render.md "Live preview": while the Agent is between two edits of one change, its facts are those of what the preview last took, which the document's page shows, read again each time they are asked until it is taken, as its file's time may not change then), and again when its file's time or its `doc.json`'s is another than the one read; nothing else holds an entry, and any of it can go and be read again (`forget`, a server's start). It keeps the one version of each document it read and never the edit service's snapshots, the merge bases of open pages (the last 50: reading every document of a workspace through them would push out the one an open page commits on; `agentMergeManyDocuments`).

`GET query` answers from them: `todos` (`{ done?, slugs?, limit? }`, 200 by default, 1000 at most: of the documents edited last first, each in its order, `[{ ref: { slug, block, text, path, nth, version }, text, done, slug, title, icon, path }]`, `icon` its document's (null for none), `version` the hash of the file the facts read the to-do from, `src/shared/todos.mjs` `fileVersion`, by which a check of it trusts `nth` while the file is still that one), `recent` (`{ limit? }`, 10 by default, 50 at most: `[{ slug, title, icon, edited }]`, `edited` an ISO time), `stats` (`{ documents, todos: { done, total }, words, editedThisWeek }`, the last those written since this week's Monday, 0:00, of the server's clock) and `activity` (`{ days? }`, 365 by default, 371 at most, as many as the record keeps: `[{ date, edits, words, reader: { edits, words }, agent: { edits, words } }]`, a day of none 0, from the day the record started at the earliest) and `document` (`{ slug }`: `{ slug, title, icon, created, edited, editedBy, words }`, one document's own facts, the times ISO, `editedBy` who made its last change of text as the record of edits counted it, `reader` or `agent` (its `seen`'s `by`: `src/workbench/activity.mjs` `writer`), null where it counted none; no such document 404 `missing`; the kit fills in the slug of the document its instance stands in), the kinds and their bounds `src/shared/workspace-query.mjs`'s.

A change goes to the pages. The preview's announcement of a document's file (`announce`'s `tell`, render.md "Live preview": once the file is taken, never half written) reads its facts again of the text it took (`changed`), and the kinds that changed since the facts the pages were last told of (`told`: those of the announcement before, or the first read of the document) are told every page of the server, documents' and custom pages' alike (never the workbench's stream), as `data <kind>` on the event stream, once for a burst (`tellData`): `todos` (a to-do's words, place, check or id, or the document's title; and any change of the text of a document that has an item without an id with a twin, the same words under the same headings, whose refs carry the file's version, by which a check of it finds it by its place: the refs the pages hold must say the version it has), `recent` (its time, title or icon), `stats` (its words, its count of to-dos or done ones, its time), `activity` (an edit counted, below), `document` (its title, icon, made or edited time, or words); a document's folder made or gone tells `todos`, `recent`, `stats` and `document`. It is never weighed against what a query read meanwhile: a read between the write and its announcement (a page's query, the menu's count, the search) reads the new facts already, and the pages that read before it would hear nothing if it were. A page's live script hands it to the kit as `doc-workspace-change`, which tells the blocks that read that kind (`data`), and changes nothing else: neither page ever reloads for a message it does not know (a document's page once reloaded for any). A page whose stream connects again after it was lost (the server restarted, or slept) tells each kind as changed, as what was written meanwhile was told to no one. So a block reads the workspace through the page's one stream: no block opens one of its own (a browser holds six connections to a server, and every open page one already).

The record of edits (`src/workbench/activity.mjs`, `createActivity`) is `.gallery/state/activity.json` (`layoutOf().activity`, beside the edit state): `{ version: 1, since, days: { "<YYYY-MM-DD>": { "<slug>": { reader: [edits, words], agent: [edits, words] } } }, seen: { "<slug>": { mtime, hash, words, by } } }`, `by` who made its last change of text (`reader` or `agent`, as that edit was counted; a write of the same text keeps it, one caught up at a start is the Agent's, a record that starts afresh knows none), which `query("document")` answers as `editedBy` (`writer`). Written a second after a burst of changes (`writeAtomic`; one that cannot be written lasts as long as the server), and as the server closes or stops; the days more than 53 weeks back (`KEEP_DAYS`, 371: as many as the 编辑热力图's widest card draws, whose first square is 370 days back on a Sunday, so that a record older than that shows none of its first week as not recorded yet) go as it is written. It holds no word of any document, only counts, and only the owner runtime inside the shared service writes it.

### Annotations

**批注** is the reader's way to hand a local Agent suggestions about a document, each about words of it or blocks taken whole (`features/annotate/`; the page's side is `editor/page/annotate/`, docs/editor.md "Annotations"). One is written in the page at any time: the format bar's 批注, the button right of a block, Ctrl+Alt+M. The page always draws them, from its start: the marks on the words, the cards right of the column or, with no room for those, the markers in its right gutter (docs/editor.md), a page swapped in being told `annotate` before it is shown, so that it comes with them. The top bar's button lists those there are. It stands left of ☆ 收藏 (our own speech bubble drawn in line, round with its lower left a corner a little rounded, with two lines in it, the upper longer, no plus, which is for what adds one, 20 units, the weight of ☆) while the page has an annotation, nothing to list otherwise, or while its list is open (Ctrl+Alt+M with none says how to write one, on a page that can annotate: a custom page's says nothing), and as it was while its page reconnects (a switch, a reload), never for a page that says it cannot annotate (not for the 写作偏好's page or 演示视图, which have no session); its tooltip says 批注 with Ctrl+Alt+M while the list is closed, and it looks pressed (a quiet grey fill, `--bacTerTra`, no blue) only while the list is open.

**The list.** Under the button, right-aligned, 8px below it (`.annot-list`: the workbench's popover and `MenuList`, 320px wide), a row per annotation the page shows, in page order: the suggestion, the words it is on one gray line below (a block annotation's, the blocks' as they read now; 整块 for a block with none; one being emptied in its card, those words alone as its one line), both cut with an ellipsis (a `MenuEntry`'s `detail`), scrolling past 384px (`MenuList`'s `scrolled`: what is below stays). The rows come from `annotations { action: "list" }` when it opens and whenever the count changes. A click on a row closes the list and locates the annotation (`annotations { action: "locate", id }`): the page opens what hides it (a closed disclosure, a tab not shown: `DocKit.reveal`, as the outline's jump and a link to a block), scrolls it into view and brings its card in front in the margin without the focus, its words lit, until a press elsewhere (in the page, or in the workbench, the next press there saying `away`, as the page has no focus to lose); with no room for cards it shows its card by its words, as resting on a marker does, until a press in the page or its words or blocks leave the window (the pointer never came to it to leave it). Below a line, **复制批注** with the count (`N 条`) and **全部删除** (red under the pointer); with none, one gray line saying there are none and how to write one, and both are disabled (`components/Menu.tsx` rows take `disabled`).

Its moves: a click on the button opens the list, a click on it again closes it, and a press outside, the page included (the workbench hears that as its window's blur), or Esc closes it. Resting on the button does nothing. No row is highlighted until the pointer or the keys reach it, and a row the pointer has left no longer is (`MenuList`, for every menu of the workbench: a row the keys moved to stays, and so does one with a submenu). Ctrl+Alt+M (⌘⌥M) with nothing to annotate in the page opens or closes the list (`pressAnnotate`: the focus goes to the button as a click's does, or the workbench would not hear the press in the page that closes the list); the workbench registers `Mod+Alt+M` with `keys`, and the page keeps the key for itself when it has something to annotate (docs/editor.md).

- **复制批注** (`annotations { action: "copy" }`): the page saves what is typed, the server checks the annotations against the file (those whose words are gone are not copied), and the workbench writes the Markdown in the UI's language (`shared/annotations.mjs annotationsMarkdown`): a first line saying what it is and how many, the document's title, its source path (as 复制本地路径 gives it), then each annotation in page order: `## n.` and where it is (the Sheet tab's name, the h2–h4 above it, the disclosure it is in; a heading with none above it, itself; 页首 before the document's first heading, not 正文, which a tab or a heading may be named; 正文 in a document without headings), its blocks' ids as the file has them (`（整块）` for blocks taken whole; `（还没有 id，按原文找）` when they have none yet), the quoted words as a Markdown quote, and 建议： with the suggestion, each of its lines a paragraph (blank lines in it make no more of them). One annotation is said as one (以下是我对这份报告的一条批注…; in English the toasts and the first line say "1 annotation"). It is on the clipboard from the click on (a `ClipboardItem`, as 复制页面内容); the toast 已复制 N 条批注 shows even with 减少通知.
- **Done ones** (`done: true` in the item, set by `gallery notes done`; an Agent's way of saying it has acted on one). The rows of the list come with `done`; a done row's words are gray (`MenuEntry.muted`), its card in the margin and its marker are drawn quiet (docs/editor.md "Annotations"). 复制批注 leaves them out (the server's copy, and the count beside the row counts those not done; with all done it is off), and **删除已处理** (a row between 复制批注 and 全部删除, with the count, shown only while one is done; `annotations { action: "clearDone" }`, what is typed saved first) takes just those out with the toast and 撤销 of 全部删除 (the done mark goes back with them). No row marks one done: that is the Agent's (docs/editor.md; `gallery notes`), the reader deletes.
- **A removal by a command** (`gallery notes remove`, with `by: "command"`): the edit service keeps what it took for two minutes and every answer of the annotations route carries it as `commandRemoved: { at, items }` until a `put` or a `restore` of that document; a page that takes in an answer with a `commandRemoved` it has not told (by its `at`) says `annotations-removed` with those items, so the open workbench shows 已删除 N 条批注 with 撤销 as for the card's delete button. A page opened within the two minutes says it too. With no page open nothing offers it back (the command says so).
- **全部删除** (`annotations { action: "clear" }`): all of this document's (what is typed saved first), no confirm dialog; the toast 已删除 N 条批注 holds 撤销 for 6 seconds and shows with 减少通知 too. 撤销 puts them back as they were in the document they came from, whatever document is open by then: the workbench posts `{ slug, restore }` to the edit service itself (with the token `info` gives) and, when that document's page is the one open, has it read them again (`annotate { refresh: true }`).
- **The card's delete button** is the page's (docs/editor.md "Annotations"): it deletes that annotation and says `annotations-removed` with the item (so does a saved one emptied in its card as the card closes, the item with its last words), and the workbench shows the same toast with the same 撤销, by the slug of the page that said it (a draft of another workspace's page says it too, its entry the slug: 撤销 posts to the shared service's owner-prefixed annotations endpoint, which restores that document's `annotations.json` in its original folder).

They are kept in `<workspace>/<slug>/annotations.json` (`{ v: 1, items: [{ id, created, updated, text, anchor, done? }] }`), never in `doc.html`; the edit service reads and writes it (`/__gallery/edit/annotations`, below), so trash, restore and 创建副本, which move or copy the document's folder, take them along, and no export includes them.

| request | body | answer |
| --- | --- | --- |
| `GET /__gallery/edit/annotations?slug=` | | `{ ok, version, items, dropped }`, checked against the file first (`dropped`: the ids a check deleted lately, which a page that brings their words back with an undo saves again) |
| `GET /__gallery/edit/annotations?slug=&as=copy` | | `{ ok, title, path, items: [{ where, top, blocks, whole, quote, text }] }`: 复制批注's data (`top`: before the first heading), the done ones left out |
| `GET /__gallery/edit/annotations?slug=&as=notes` | | the same with every one, each also `id`, `done`, `created`, `updated`: `gallery notes`'s list |
| `POST /__gallery/edit/annotations` | `{ slug, put }` (an item, by its id) · `{ slug, remove: id }` · `{ slug, clear: true }` · `{ slug, restore: [items] }` · `{ slug, anchors: { id: anchor } }` · `{ slug, done: [ids] }` / `{ slug, undone: [ids] }` · `{ slug, removeIds: [ids] }` / `{ slug, removeDone: true }` (with `by: "command"` from `gallery notes`) | `{ ok, version, items, dropped }`, `clear`, `removeIds` and `removeDone` also `removed`; `commandRemoved` after a removal by a command; an id no annotation has: 404 `reason: "ids"`, `ids`, nothing written |

A GET checks the Host and the token (`X-Gallery-Token`), a POST is checked as a commit is; both run in the annotations' own queue (one at a time with the check after a write of the document, never ahead of a commit), and a write is atomic. `restore` never puts an item back over a newer text of the same id (`updated`: what a page typed offline and sends late). An item has words: a `put` with none is refused (`reason: "item"`), `restore` leaves such out, and a file's item with none (made between 2026-11-02 and 11-06, when one could mark a place) is read as none: not shown, listed, copied or counted, and gone from the file at its next write. `anchors` is the page telling where annotations' words went with the reader's edit, right before the commit that writes it (docs/editor.md "Annotations"): written as told, unchecked, only for annotations the file has, so the check after that commit finds them as they are. The preview's live-reload channel says `notes <version>` when the file changes (the page reads it again unless it wrote that version itself). What a check deletes because its words or blocks are gone (an Agent rewrote them, or the reader's edit did) is said, never only gone: the edit service keeps each deletion, each annotation's id, text and quote, in its state directory (`dropped-annotations/<directory>/<slug>/`, `src/editor/dropped-annotations.mjs`, as it keeps what a reader's edit wrote of natural HTML: twenty at most a document), says it in the dev server's log (`[gallery] annotations <workspace>/<slug>/annotations.json: Gallery deleted 1 批注 (annotation) whose words are gone from the document (rewritten or deleted):` and each `  <id> "<text>" on "<quote>"`), and `gallery check`, `gallery export` and `gallery qa` say it once, with its time, and take it away (docs/render.md "Build pipeline"; the hand-in answered, and `POST /__gallery/edit/settle` `{ slug, workspace }` checked as a hand-in is, once the check of the file as it is now ran and its deletions are on disk); one put back since (its words brought back by an undo, which the page saves again) is left out. A removal, 删除批注 and 撤销 are the reader's own and are not said.

### Kept in the browser

What the UI keeps in the browser (the workbench and the document pages share one origin, so one storage) is named in `src/shared/renamed-storage.mjs`: `localStorage` `gallery:language`, `gallery:preferences`, `gallery:outline-open`, `gallery:outline`, the emoji picker's `gallery:emoji-skin-tone`, `gallery:emoji-frecency`, `gallery:icon-picker-color`, `gallery:recent-glyphs` and `gallery:glyph-set`, and the workbench's `gallery/workbench:sidebar`, `:theme`, `:tree`, `:favorites` and `:present-zoom`, and `:updated` (the pages someone else wrote that the reader has not opened since, **Updated elsewhere**: a key made after the rename, in `NEW_KEYS`, with no old name to carry); `sessionStorage` `gallery-workbench:shown` (the page the report area showed as it went, for its next load to tell the same page loaded anew: `shared/kept-view.mjs`, "Where the reader was"; also in `NEW_KEYS`, short-lived and one tab's, so nothing to carry); the IndexedDB database `gallery-workbench` (the chosen export folder's handle, `workspace/exportFolder.ts`). Every module that reads or writes one takes its name from there (`KEYS`, `NEW_KEYS`, `DATABASES`), so that module has run before any of them reads, whichever page of the origin loads first. Not named one by one: the editor's `gallery-edit:*`, made per document and per tab (the unsaved edits, the tab's view, the lost list, the menus' recent choices: `editor/page/autosave.mjs`; the headings folded, `gallery-edit:heading-folds`: `editor/page/fold/`), carried by their prefix (`PREFIXES`, below); not here: the kit's reading state (`gallery:<report>:<id>`, [render.md](render.md)), which carries its own keys the same way.

Before the product's rename (2026-10-26) the same were kept under `html-report-studio:*`, `report-studio:*`, `html-report-studio/workbench:*` and `html-report-studio-workbench` (`OLD_KEYS`, `OLD_DATABASES`). Nothing old is removed: a page or workbench of the old version still open goes on with them. As the module loads (and on the storage event, when another tab changes an old key) each old key is carried to its new one: the first time it is looked at, only into an empty new key (a new key written already wins); again whenever it changed since it was last looked at, which only a page of the old version does, so what it wrote is the reader's latest, removal included (a theme or icon set back to its default). What each old key held when last looked at is kept as a digest under `gallery:renamed` (in each storage), so a carry is done once and runs again with no change, and a key the new version removed stays removed. A failure (full or blocked storage) leaves that key to the next load. The export folder's database is carried by `carryDatabase` before its first use on a page: each entry of the old database's `handles` store the new one does not hold, the old looked for (`indexedDB.databases()`) and never made, changed or deleted; a failure leaves both as they were and is tried again next time (the browser asks for the folder's permission again, as after any restart).

Until 2026-10-28 the editor's keys were `report-edit:<slug>:<kind>[:<tab>]` and `report-edit:<name>` (with the edit routes' old name, decision E of the CLI). They are carried by their prefix (`PREFIXES`, `prefixPairs`) under the same rules, in `localStorage` and `sessionStorage`: every old key under it there now, and every one looked at before (so one removed since takes its new key with it), each to the key of the same name under `gallery-edit:`, what it holds as it is; the editor's page loads the module before any of its own. So a crash buffer an old page left is sent by the page of the new version when it opens; the old key stays and, unchanged, is not carried again. A page of the old version still open can no longer save (its routes are gone): reloaded, it is a page of the new version and sends what it kept. The 写作偏好 dialog, which forgets what a page left unsaved, forgets it under both prefixes.

### Presentation

What an export (or a view copy) made of it is undone at its place, each step mirroring one of the render's (docs/render.md "Build pipeline"): the export's generator and policy after `<head>` and the browser tab's icon before `</head>` go, each with the line break the export put with it; the kit's tags and an export's inline copies of them go (in its head or its body; an older file may write them in its main), and so do a view copy's id, reading state and policy, each with its line when it has one to itself; an icon's picture (the page's, a highlight block's) is its emoji again, an icon of the 图标 tab's SVG goes (its `data-icon` says it), a Sheet tab's emoji picture goes (the Twemoji picture of its `data-tab-icon` alone: a picture the author gave the tab stays); and each file the export embedded, a `data:` URL at a place an export holds a file of the folder (`referencesWhere` in `render/asset-references.mjs`, the media blocks' places among them: an attribute, a `srcset` candidate, a `url()` in a style attribute or in any of its `<style>` elements), is a file of the new document's folder again, written in its place (`addressEdits`), as is a file that a `report.html` names (`assets/<file>`) and that comes with it (its folder zipped, or chosen with it): such a file is the document's, never a page of its own, a CSV, a PDF or an HTML file among them. The new document is that page, its main's `data-doc-id` the new slug (a main with nothing after its header gets the starter's empty paragraph, to write in); report.json gets its title (the header's title's text, else the `<title>`'s) and its icon, and `导入自 <file>` as its description, as any import's (an export carries no report.json: a description, `type` or `source` of the first document's stays behind). Worked back from the page, an export does not carry a file's own name (but where it carries its source, above): each comes back named as an upload is (`<kind>-<hash>.<extension>`, the extension its media type's or its link's `download` name's; a bookmark's icon and cover under their own stems, `bookmark-icon-…`, `bookmark-cover-…`), so a file the editor uploaded keeps its name and one an Agent named (`assets/photo.png`) is renamed, a link that gave no `download` name now gives the file's (the export wrote it), and a link's file that is also a picture or a frame of the document (the same bytes) is that one file, under its name. Nor does it carry a `srcset`'s smaller candidates (it keeps the largest) or a cropped picture's original (`data-original`, not embedded: the import leaves it out, and `data-crop` with it, unless a folder chosen with a `report.html` holds that file), and it writes a few things one way for two, which come back in that one way: a Sheet tab's `style` that ended in `;` or not, blanks around an icon's emoji, a byte order mark (dropped). Exported again, an imported document is the first export but for its slug, the sha256 it says, what it carries (which holds the slug) and a dropped crop's two attributes (worked back from the page, a byte order mark too). In a zip, a page in the folder named as another (Notion's `Page <id>.md` and `Page/`) is that one's subpage, and so is one only another links to in a paragraph of its own (that paragraph goes: the sidebar shows subpages); subpages are in the order the links give. Files chosen together are read as one folder, so a Markdown file brings the pictures chosen with it (a link into a folder, `assets/dot.png`, finds one chosen with it by its name). A toast says how it went: 「<name>」已成功导入, 你的文件已成功导入, 已导入 N 个页面，M 个文件不支持：…, or 不支持的文件类型, and names the pictures a page links to that were not found (已导入，N 张图片没有找到：… · and how to bring them: choose them with the file, or zip its folder when they are in another); the first page imported opens.

### Typical flow

1. `GET /__gallery/workspace/info` for the token, and `GET /__gallery/workspace/outline` for the sidebar.
2. Open a report: an iframe on `/generated/<slug>.html`. Wait for `ready`, then follow `state` for where saving stands (pending, saving, offline, conflicts) and for the title.
3. Before switching away or closing, send `prepare-close` (it answers within a second, and always lets the page go). Before exporting or copying the open document, send `save`.
4. Rename from the sidebar with `POST rename`, or with `set-title` when that document is the open one (its page then saves it, and nothing writes the file under it); a row's icon likewise, `POST icon` or `set-icon`. From the open page, `edit-title` has the reader type the new title where it is.
5. Report-level operations go through the POSTs above; read the outline again after each. Close an open document (`prepare-close`) before moving it to the trash: a page reloads when its file goes and finds nothing there.

### Status (gallery status)

What the reader has open, for an Agent that is told "this document", "this paragraph" without a name (since 2026-11-11). Pure shape and cuts: `src/shared/presence.mjs`; the server's memory: `src/workbench/presence.mjs`; the tab's side: `src/workbench/app/session/presence.ts`, started once by `main.tsx`; the command: `src/cli/status.mjs`; held by `tests/unit/status-notes.mjs` and the scenario `statusOpen`.

- **The tab reports.** Each workbench tab (a random name made when it loads) posts `POST /__gallery/workspace/presence` (checked as any change: Host, Origin, the token; outside the queue, so a heartbeat waits behind no save) with what its connected session says: the entry open (a slug, `~ws-xxxxxx/<slug>` for a draft of another workspace, `@<slug>` for a custom page), the title the page shows, `visible` (`document.visibilityState`) and `focused` (`document.hasFocus()`, true while the focus is in the page's frame), the session's flags (`state`: pending, saving, offline, conflicts, unfit, changed), the 批注 count, and the session's `focus` (the caret's block, the selection). It reports when that changed (debounced 300ms; `touched` when the reader did something: a different document, the caret or selection moving, changes starting to wait for saving, the tab shown or focused (an Agent writing the file, the page shown again, the 批注 count changing are not use)), every 20 seconds as a heartbeat (not "used"), and `{ tab, gone: true }` when the tab goes (`pagehide`, with `keepalive`) or shows nothing a report is about (a web link, a document that is loading is simply not reported). A failed post is forgotten: nothing is said to the reader. A web link and an extension's page are not documents and are never reported.
- **The server keeps them in memory** (`createPresence`, one store for every workspace the server hosts: `createProjects` makes it, each runtime's workspace service takes it): the record of a tab, `used` (when a report with `touched`, or the first, or one for another entry, last came) and `seen`. A tab not heard from for 90 seconds is dropped (a crashed browser, a computer that slept; a tab hidden for long is throttled to a timer a minute, which that outlasts); `gone` drops it at once. `cleanReport` cuts everything on the way in: an entry must be a slug / draft / page key, a block an eight-character id (else null), the words 200 characters, 20 blocks, counts numbers; anything else makes the report none (400).
- **`GET /__gallery/workspace/status`** answers `{ ok, open: [entry], last }` — the tabs the reader used last first (`last` is the first). It needs the Host **and** the token (`X-Gallery-Token`; a GET carries no Origin): the words of a selection are the reader's. An entry (`describeTab`): `tab`, `kind` (`document` or `page`), `slug`, `title`, `file` (the document's `doc.html`, a page's `page.html`, absolute, in the workspace it is in) and `workspace`, `visible`, `focused`, `idle` (seconds since the reader last did something there), `save` (`saveOf`: `conflict` when the page holds a conflict or content the document cannot hold, else `offline`, else `pending` for changes waiting or on their way, else `saved`), `conflicts`, `notes`, `caret`, `selection` (`truncated` when its words were cut).
- **The command** asks the server the announcement names (`findPreviewServer`, answering), reads only, and starts nothing; with none it prints one sentence and exits 0 (`{ "running": false, "open": [] }` with `--json`). A document that is pending, in conflict or offline gets a `问题：` line (the reader settles it on the page first, then the Agent changes the file), and the first entry with a selection or a caret a `提示：` on finding its block by `data-block-id`. Only a workbench tab reports: a document opened on its own at `/generated/<slug>.html` is not in the list.

## Plugin loading

Plugin assets, icons and backend requests inspect only the requested plugin's manifest, through the same directory discovery, configuration and file validation as the full list. Each request reads current permissions and revisions. The backend monitor skips disk scans when it has no child processes, inspects only its existing children otherwise, and never overlaps a previous monitor pass.

## Global appearance and login startup (2026-11-11)

- 「设置为全局默认」 keeps the existing POST workspace/looks route, accepting a document slug at its owning project path. ## Extension development and previews

Writing preference tab menus use the shared popover with a preference-specific layer above the dialog. Clicking the selected tab or right-clicking any tab opens its operations; Escape closes the menu before the dialog.

When no extensions or standalone sidebar columns are installed, the dialog keeps the supplied original design's centered puzzle icon, title and short installation hint, followed by a full-width install button. It has no footer about installation paths or CLI commands. The expanded path input has 8px above and below; the install button, input and ZIP picker share their left edge. Installed entries continue to use the card grid and details below.

Extension settings reuse component cards and a detail view, with sidebar-only columns in the same grid and install last. Details hold descriptions, paths, backend logs, Agent files and removal. Runtime errors are revision-scoped and shown in the card/detail; obsolete reports are ignored. Watchers invalidate an extension for nested dependency changes without rescanning every file on each request. Versioned module paths also invalidate relative imports. A workbench script is an ES module whose `activate(api)` is the only way in (`features/extensions/runtime.tsx`): there is no global `window.gallery`, and nothing marks a script as needing a refresh. A module that exports no `activate` is an extension error like a throw: the runtime reports 工作台脚本需要导出 activate(api) (Gallery's words, without its own stack) as the revision's workbenchError, toasts 扩展 {0} 加载失败 and shows 界面错误 on the card; the same revision is not imported again until its files change or the extension is enabled again (the browser keeps the module, so it is not evaluated twice). Scripts reload and recover after fixes. Running backends restart on dependency changes; replacement and shutdown share the existing child lifecycle.

**An extension's own settings** (`shared/extension-settings.mjs`, skills/gallery/references/extensions.md "Settings"). `extension.json`'s `settings` is a list of `{ key, type, label, default?, help? }`; `readManifest` refuses one that `settingsProblem` finds wrong (the first thing: not a list, more than 50, a key not an identifier of `[A-Za-z_][A-Za-z0-9_]*` up to 64 or one an object has, `__proto__`, `constructor`…, a key twice, a type not in `SETTING_TYPES`, a label of none or over 100, a help over 500, a default not of its type), so an unknown type is the manifest's error and `extension check` fails with it. Only `boolean` is in `SETTING_TYPES` (`valid`, `empty` its value with no default, `parse` a command line's word); a type is a line there and a control in `SettingRow`. The user's values are kept beside the switch, in the default workspace's `gallery.json` `extensions.<id>.settings`, only those that differ from the default (`storedAfter`), so that a default changed later reaches those who never chose (`setExtensionEnabled` now writes the switch alone, keeping the rest of the entry). Every declared key's value (`settingsValues`: the user's where it is of its type, else the default) is what `GET /__gallery/extensions` lists as the item's `settings` and what the backend reads: `syncSettingsFile` writes `<default workspace>/.gallery/extensions/<id>/settings.json` (`layoutOf().extensionData`; not in the extension's folder, whose writes the recursive watch of Windows and macOS reports as the folder's change, a new revision that would restart the backend, and which an update replaces) in `launch` before the backend is spawned, its path in `GALLERY_EXTENSION_SETTINGS`, and again at each change; the writes are queued one at a time in the service (the only process that runs backends; a command goes through it while it runs), each from `gallery.json` as it then is, so a start and a change cannot leave the older values last. `POST /__gallery/extensions/settings` `{ id, values: { key: value } }` (`setExtensionSettings`, under the outline's lock as the switch is) answers `{ settings, file }`, 409 `reason: "disabled"` for an extension switched off, 400 `reason: "settings"` for a key it does not declare or a value of another type; it is no mutation (no backend stopped, no request held) and tells the workbench (`extensions <id>`) when something changed. The detail draws the settings after the description as 组件列表's switches (`.comp-opt`, `.ext-setting[data-key]`), greyed with a tip while the extension is off; a click posts and reads the list again. The runtime keeps each loaded script's values (`api.settings`, frozen) and, when a refresh lists other values for the same revision, sets them and calls each `api.onSettings` callback (which reports at once, as `onRoute`; cleared on dispose), with no reload. `extension remove` takes the `gallery.json` entry and `.gallery/extensions/<id>/` with the folder (`forgetExtensionGrant`). `gallery extension settings <id> [key=value…] [--json]` reads and sets them the same way (`src/cli/ui-commands.mjs` names it for 拓展列表).

The backend's address is `/__gallery/extensions/<id>/api/` (`server/extensions.mjs` proxies it to the backend's `/`, with the token and same-origin checks). `activate(api)` gets it as `api.backend` (absolute, ending in `/`) and as `api.fetch(path, init)`: `path` is resolved against it with its leading slashes dropped (`'publish'`, `'/publish?x=1'`), anything else (a scheme, a backslash, a `..` out of it) throws a TypeError (api.fetch 只接受这个扩展后台里的路径…), and `X-Gallery-Token` is set on `init.headers`; the answer is the browser's Response, nothing read from it. Since 0.2.4 scripts are served at `files/@revision/<revision>/`, so an address an older script works out from `import.meta.url` (`new URL('../api/', …)`, the backend when scripts were at `files/<file>`) lands at `files/@revision/api/…`. There is no alias for it: the files route answers a request it cannot serve whose path (after a valid revision) has an `api` segment, a method other than GET or HEAD or a file that is not there, with 404 `{ ok: false, reason: "backend-address", backend, message }` (`said()`, the backend's address and api.fetch/api.backend in it) instead of the missing file's 400 or the 405; the message is also the revision's workbenchError (kept apart from the script's own reports, which an activation that goes on afterwards would clear, and gone with the revision), so the card shows 界面错误 and `extension check` fails with it. A request to a disabled or removed extension is answered 403 `{ reason: "disabled", message: 扩展已停用 }`; so is one that disabling breaks off: the switch is written before the backend is stopped, so when the proxied request fails (its socket reset), or the request was still waiting for the backend to start, the proxy reads the switch again and answers as for a request after it, a 502 only while the extension is still enabled (a crash, a timeout). The answer is the server's, not the workbench's: a disposer cannot be waited for by every tab, and the CLI disables with no tab open.

`gallery extension new <id> <title> --ui --server` generates activate/dispose and Node HTTP templates that run as they stand: with both, the sidebar-footer button asks the backend's `GET /hello` with `api.fetch('hello')` and toasts the answer (`src/cli/extension-template.mjs`), and `new` lists each file with what it does. `extension check` validates manifests and tests activation/backends in the existing disposable sandbox (it waits for the workbench's one `POST workbench-error` about the script, the error or the empty report after `activate` returned, at most 20 seconds, then reads workbenchError), captures errors and optional screenshots, and leaves the original switch unchanged; `--press <button>` clicks that slot button (aria-label or words) and prints each request to the backend's `api/` with its status and answer and each toast, failing on a failed or 4xx/5xx request, an error toast or a throw, with the backend's log. Its failures name the extension's own files: the sandbox copy's folder and the served `files/@revision/<hash>/` addresses are rewritten to the source folder (`ownPlaces`).

`gallery preview` embeds an authored page, current Gallery styles and `src/preview/` runtime/shell into standalone HTML. Its toolbar selects theme, width and custom states; screenshot generation uses the existing isolated Chrome/Edge launcher. It is a design tool, adds no approval requirement and writes no workspace data. See `skills/gallery/references/previews.md`.
